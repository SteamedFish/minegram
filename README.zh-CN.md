# Minegram

Minegram 是一款关于「有序地雷串」的网页解谜游戏。每一行、每一列都由其中显著地雷串的长度来描述，
并且**每一个生成的棋盘都会先被证明**只有一个解，然后才交到你手上。

本应用现在在同一个入口之下提供两款游戏：**Minegram**，即下文介绍的有序地雷串解谜；以及**星战**，
一款 n × n 的放星解谜游戏——它的棋盘同样保证唯一解，而且是**由构造方式保证**的，每一张棋盘都会
在生成时附带唯一性证明。每次载入应用时，你会在**游戏选择界面**上挑选要玩的游戏。该界面预留了分游戏
记录（已玩局数、最长连胜）以及标出上次所玩游戏的圆环，但两者都还没有接上——目前没有任何一款游戏会
记录这些数字，凭空造数字等于撒谎——因此每张卡片都显示「尚未游玩」。

两款游戏都已经可以游玩。完整的产品契约、生成算法、交付阶段与验证预算见
[`plan/PLAN.md`](plan/PLAN.md)。

## 玩法

每一行和每一列都带有一个形如 `3 5 1` 的数字标注：共 9 颗雷，分布为连续三颗、间隔、连续五颗、
间隔、一颗。**顺序有意义**——`3 5 1` 与 `3 1 5` 描述的是不同的棋盘。任意两串之间的间隔至少有一个
无雷格子；地雷串也不必是极大串，因此 `3 5 1` 出现在 12 格的行上也是合法形状。

终盘棋盘的每一行、每一列都至少有一颗雷，所以标注里永远不会出现 `0`，也不存在无意义的行。

- **标记**某个格子为地雷或空白。标对了，该格会被锁定。
- 标**错**扣 1 分。之后可以改正，但分数不退还；分数扣到 0，游戏结束。
- 重复声明某个格子已经拥有的标记是免费的，不会产生任何变化。
- 当某一**行或列的地雷全部被标出**，且该行/列没有标错时，游戏会**免费**替你把这一行/列剩下的格子
  全部填好。你永远不会被扣除由游戏代填的格子。
- 某**串地雷全部被标出**时，对应的数字会立即高亮——不需要先标出它前后的间隔，间隔由游戏来填。
  因此在一列 `7 2 2 1` 上标好 `7`、`2`、`2` 之后，这三个数字会一起高亮，而尚未标出的 `1` 保持普通。
- 当每一个格子都带有正确的标记时，本局获胜，并自动开始下一局。

### 操作

- **左键拖动**可用当前模式连续涂一串格子，**左键单击**只标一格。
- **右键拖动**以相反模式涂格子，且不会改变你当前选中的模式；**Shift + 右键**擦除单个格子。
  `擦除`本身也是一个独立的模式。
- 每个拖动都有非拖动的等价操作：工具栏中的模式选择器加上方向键导航，因此整个游戏都可以纯键盘
  操作。
- 主题默认跟随系统，也可在页脚固定为浅色或深色。界面提供英文与简体中文。

## 星战（Star Battle）

星战是第二款游戏，与 Minegram 平级，而不是它的一个模式。每次载入应用都会先进入**游戏选择界面**——
这是有意为之：不会直接把你丢回上一局，每位回来的玩家都要重新选择。每款游戏是一张卡片，写有名称
和一句话介绍。

### 规则

- 棋盘是 **n × n** 的格子，上面恰好有 **n 颗星** 与 **n 种颜色**，每个格子都被染色。
- 每**行**恰好一颗星，每**列**恰好一颗星，每**种颜色**恰好一颗星。
- 任意两颗星不能相邻——包括斜向。每颗星会排除它所在的整个 3 × 3 区域。
- `n` 默认为 **10**，支持范围是 **4 到 15**。下限是 4，因为更小的棋盘根本不存在合法放法：星的位置
  必须构成一个相邻行距离至少为 2 的列排列，而这样的排列在 n = 2 和 n = 3 时不存在。上限 15 是产品
  层面的选择——这是现有配色与网格无需新增 CSS 即可覆盖的最大棋盘。工具栏上的**棋盘尺寸**控件可以
  选择 `n`，且选择会被记住；上下限读取自 `MIN_STAR_SIDE` / `MAX_STAR_SIDE`，而不是重复写死字面量。

### 玩法

每个格子最终都必须带有正确的标记：**空白**（无星）或**星标**。

- **标记**某个格子。标对了，该格会被锁定；已锁定的格子会静默拒绝之后的任何声明（撤销同样在内），
  且永不扣分。
- 标**错**一颗星扣一条**生命**。错误的标记会保留在棋盘上以便改正，但生命不退还。生命默认 **5**，
  工具栏里可以把上限设为 1 到 9 之间；扣到 0 本局结束。把格子误判为空白不扣生命——只有「声称这里
  有一颗星」才可能错，「声称这里没有星」不会。
- **撤销**某个格子——按 Backspace / Delete，或单击它已携带的标记——可以把它恢复到未标记状态。撤销
  免费、不退分、也永不锁定。
- 重复声明某个格子已经拥有的标记是免费的，不会产生任何变化。
- **标对了星，它顺带排除的格子会由游戏替你填上**：同一行、同一列、同色其余的格子，以及它的
  3 × 3 邻域，全部变成已锁定的空白，就发生在同一次操作里。这些格子本来就是规则蕴含的排除，所以
  它绝不会告诉你星**在哪里**，只是省掉你记账的功夫。它也**绝不覆盖**你已经做过的标记——包括你
  已经为它付出一条生命的错星——而且不收费。
- 落在同一个 3 × 3 区域内的两颗星会在两个格子上同时被标出。这是唯一一条无法靠计数从盘面读出的
  规则，所以它是游戏唯一还会替你画出来的冲突。
- 当**每一个格子都带有正确的标记**时，本局获胜。

### 操作

**点按**标记一颗**星**——这才是这个游戏真正要你做的断言，所以点按就该做这件事。**右键单击**，或
触屏**长按 500 毫秒**，切换**空白**。**拖动**会用这次手势的工具涂满它经过的每个格子，每个格子一次
笔画最多被涂到一次。棋盘上方的规则说明会用文字把这件事讲清楚——需要玩家自己去猜，正是它在手机上
没法用的原因。

键盘：整个网格只有一个可停留的 tab 焦点（roving tab stop）。**方向键**移动，**Home** / **End** 跳到
行首/行尾（配合 Ctrl 跳到棋盘两端），**空格**或 **Enter** 切换空白，**s** 或 **\*** 切换星标，
**Backspace** / **Delete** 撤销标记。

工具栏会标明当前正在玩的是哪款游戏，并提供返回游戏选择界面的入口；每个屏幕上这样的入口只有一个。

### 难度

每个难度档标注的是**解开这块盘需要用几种独立技巧**。这个数字是实测的，并且在生成器验收每一块盘时
强制校验，而不是嘴上说说：

| 难度档 | 中文 | 这块盘的要求 |
| --- | --- | --- |
| `starter` | 入门 | 只用基础规则就能解完，约 3 波传播 |
| `steady` | 进阶 | 只用基础规则就能解完，但推理链很长——按尺寸 13 到 29 波 |
| `challenging` | 挑战 | 基础规则**卡死**，需要恰好一条额外技巧 |
| `expert` | 专家 | 基础规则卡死，单条技巧不够，需要两条 |
| `contradiction` | 反证 | 基础规则卡死，且**任意**技巧组合都不够，只有反证能解 |

这里的「技巧」指线约束——某个颜色只能在特定的几条线上放星，也因此「几个颜色被挤在同样几行」能推出
东西。前三档是直接构造出来的；后三档来自一个带种子的搜索，它逐格改色直到基础规则不再推进，然后枚举全部
十六种技巧子集逐一复验每块被接受的盘。

**这是一个诚实的测量，不是一把标定好的人感觉刻度。** 更长不一定对人有更难：玩家挑出来觉得有意思的四块盘里，
评价最高的那块只需要**一条**技巧，但要 12 波才兑现，而我们最容易的一条技巧盘只要 4 波。所以请把档位名字
当成对这块盘**形状**的描述，而不是当成难度结论。

`contradiction` 档在目前观测到的所有盘上都只用**一层**假设——还没有哪块需要「假设之上再假设」。这也正是当前
求解器能造出来的上限。

生成开销：基础档在 n = 10 约 1.1 毫秒，n = 15 约 2.8 毫秒（每点各测 200 张盘）。技巧档慢得多，因为要搜索——
n = 10 时约 36 毫秒和 150 毫秒，n = 15 会到秒级。难度选择会被持久保存，更改难度会用同一颗种子重新生成
一张棋盘。

### 唯一解来自构造——并且带有证书

与 Minegram 的「搜索加证明」式生成器不同，星战的棋盘**由构造方式保证唯一解**，且验收环节会对
每张棋盘加以证明：

- 棋盘有解，当且仅当存在某个列的排列 `T`，满足 `|T(r) − T(r+1)| >= 2`——每行每列各一颗星，彼此
  正交或斜向都不相邻——并且它选出的 n 个格子颜色两两不同。
- 生成器按**长条 + 大海**方式染色。星星的排列会被要求前两颗星各占一条边缘列，再由每个难度决定
  铺下多少条横向长条；没有被长条或星星认领的格子，全部归入一个巨大的吸收性**大海**区域。长条里的
  每一格都与一颗已被强制的星同行，因而可以被证明为空白，所以每个区域只剩一个可行格，颜色规则会把它
  强制确定。归纳下去，n 颗星全部被强制确定，而被完全强制的星集合就是唯一的解。
- **每种颜色都恰好构成一个连通区域。** 生成器会统计每个颜色的连通分量，一旦某个区域裂开就丢弃该
  棋盘，所以这是结构性保证而不是碰巧成立。上一版构造做不到这一点——它在**所有难度档**上生成的全连通
  棋盘数量都是 0，因为一个颜色的格子会形成一条横带，中间被相邻区域的星挖出一个洞，分裂成两半。
  而受害最重的并不是最难那一档：`starter` 最惨，n = 10 时最差的区域裂成 13 块，n = 15 时裂成 25 块。
- **大海会占据棋盘的大部分，而玩家不喜欢这一点。** 因为它吸收一切未被认领的格子，有一种颜色会覆盖
  大部分盘面：`starter` 不铺长条，n = 4 时占 81%，n = 15 时占 94%，盘面上散着 n 个各自不同颜色的单格。
  玩家明确说过「长条+大海的构造实在是过于简单了，丧失了非常多的趣味性」，而这个抱怨背后的测量是
  **结构性的**：大海在**任何盘面尺寸、任何难度下都与其它所有区域相邻**，也就是它是区域邻接图里的
  **枢纽**。玩家从他们真正在玩的游戏里挑出四块盘实测，**四块都没有枢纽**——最大区域占盘面 25% 到
  40%，而我们是 39% 到 59%。无论怎么重编号、怎么分配色相，都无法把一个枢纽的颜色与任何颜色分开，
  所以「相近颜色尽量远离」有一半只能由调色板来给；但另一半是布局问题，而答案不是去调色相，是
  **根本不要有枢纽**。
- **难度不是按波数分级的。** 在四块参考盘和我们自己的输出上实测，波数分不开档位：一条技巧的盘跨
  3 到 5 波，两条技巧的盘 4 到 8 波，反证盘 3 到 8 波——重叠严重。波数量的是**求解器**要磨多久，
  不是人觉得有多难。
- 验收使用的是**波传播求解器**（`propagateStarBoard`）：冻结状态、算出所有被强制的移动、同时应用，
  记为一波。只有传播能完整解出的棋盘才会被交付——这比「解的数量为 1」更强。因此每张生成的棋盘都
  自带唯一性证书，生产路径上完全不需要计数。
- `countStarSolutions` 仍然作为**独立的精确计数器**存在，用于测试交叉验证（在 n ≤ 10 上与构造
  逐一比对），另有一个预算受限的变体，其「预算耗尽」结果绝不可能被误读为一个计数。
- 拒绝采样经过实测并被否决：在分布均匀的染色方案中，n 超过约 8 之后唯一解的概率为零，所以无论
  重试多少次都不可能把它当作验收门槛。

### 如何分辨颜色

颜色本身承载着规则，所以调色板是推导出来的，不是手挑的。它是一个 **5 个色相槽 × 4 个明度层级**的
网格——`slot = i mod 5` 决定色相，`level = floor(i / 5)` 决定明度，并且色相再随层级偏移 36°，这样跨
层的一对颜色在明度之外还带有色相差。优化目标是**任意两色感知距离的最大最小值**，覆盖 4 到 20 的每个
前缀，因为任何一对都可能贴在一起，只有最差的那一对才决定成败。

实测最差色对（CIEDE2000）：浅色主题从 n = 4 的 26.4 降到 n = 20 的 18.0；深色主题从 34.1 降到 13.7。
作为对照，旧调色板的最差色对约为 **4**——基本等于分不出来的相邻格，也就是你实际遇到的问题。浅色与深色
是两套分别算出来的调色板，不是互相取反。

为什么单靠色相解决不了这件事：15 种颜色均分色轮是 24 度一个间隔，这已经处在人眼分辨大块平铺色块的
边缘。所以色相撑不住 15 色，调色板必须把明度也花进去。在此之外**没有**再加斜纹或字形通道——数字说明
两个通道已经够了，再加第三个只会让格子更难读。

生成过程在 Web Worker 中运行，支持取消与过期结果保护；生成失败会显示重试入口，绝不会被悄悄吞掉。
每个格子的完整状态都在它的 `aria-label` 中，整个游戏只有一个礼貌级别的 `role="status"` 区域，
负责播报错误标记、相邻冲突与胜负。配色与网格纯由 CSS 实现，更大的棋盘会在自己的窗格内滚动，
而不会撑破布局。获胜的一局会让横幅停留 2500 毫秒，然后自动生成下一局；页面处于后台时这段时间
不会流逝，横幅上的按钮可以立即开始下一局。

## 配置

| 项目 | 默认值 | 范围 |
| --- | --- | --- |
| 行数 / 列数 | 15 × 15 | 每边 1–24 格，总计不超过 576 格 |
| 雷密度 | 60% | 实际雷数在 `max(rows, columns)` 与 `rows × columns` 之间截断 |
| 难度 | `starter` | 见[难度](#难度) |
| 种子 | 0 | 任意字符串或数字；同一个种子永远生成同一张首局棋盘 |
| 初始分数 | 5 | 任意正数 |

界面上只显示你**主动输入的种子**。首局之后的每一局都由它派生出的新种子生成，而派生值从不显示——
只有在你主动索取时，它才会出现在剪贴板诊断报告中。

24 格的边长上限是一个真实的能力上限，而不是搜索预算：求解器需要枚举单行的所有合法图案，这个枚举
才是真正的瓶颈。25 × 25 一定会以 `resource-limit`（资源上限）诊断失败关闭，而不是发给你一张未经
证明的棋盘。

## 难度

难度是「强制传播之后所需的最少二元猜数」的**精确值**——也就是纯逻辑卡住、你必须做出一次
二选一押注的次数。

| 难度带 | 所需猜数 |
| --- | --- |
| `starter` | 0——纯逻辑直接可解 |
| `steady` | 1–2 |
| `challenging` | 3–5 |
| `expert` | 6 或更多 |

如果你指定了某个难度带，生成器会持续尝试，直到达到你指定的尝试次数上限，届时会**明确告知**它
无法达到该难度，而不是悄悄递给你一张更简单的棋盘。

**已知限制。** 在有界的 6 × 6 – 10 × 10 搜索、约 2,300 张随机唯一解棋盘，以及**全部**唯一解的
3 × 3 与 4 × 4 棋盘上，生成器从未产出过任何需要哪怕一次猜测的棋盘。实际上这意味着，非 `starter`
的请求会返回带有类型的 `difficulty-not-found`（未找到该难度）结果。这在
[`plan/TODO.md`](plan/TODO.md) 中记为待办事项，而不是「不可能」的结论。

## 架构

四个层级的依赖方向是向内的——`domain` ← `engine` ← `application` ← `ui`——任何一层都不会向外
依赖。`src/ui/layerBoundary.test.ts` 会解析源码中的每一条 import 边（含注释与字符串内部）来强制
这一点，因此组件无法触及棋盘、谜题、证明或推理轨迹。

- `src/domain/`——按行优先的二元棋盘类型、尺寸与坐标校验、有序数字标注编解码、标注推导。值为 0 的
  项被接受为无操作别名；规范化会把每一项校验为非负安全整数，并返回冻结的规范化数组。
- `src/engine/`——带种子的随机流、求解器、生成器与难度分析。全部不依赖 DOM，在 Worker 或 Node 中
  运行结果完全一致。
- `src/application/`——游戏 reducer 与它的选择器。权威状态不可变，除投影之外绝不离开这一层。
- `src/ui/`——组件、闭包私有的 store、文案字典与快照投影。组件只能看到选择器的输出。

星战遵循同一套向内依赖的分层，Worker 在不改变领域类型的前提下适配引擎：

- `src/domain/starBattle.ts`——谜题类型、标记常量与尺寸边界。`MIN_STAR_SIDE` /
  `MAX_STAR_SIDE` / `DEFAULT_STAR_SIDE` 是支持范围的唯一事实来源。
- `src/engine/starBattle/construct.ts`——「长条 + 大海」构造生成器，并按连通分量强制每种颜色
  连成一块；每张被接受的棋盘在离开引擎之前都会经过传播求解器的证明。
- `src/engine/starBattle/propagate.ts`——波传播求解器：生产环境的唯一性证书与深度度量，一次遍历
  兼得。
- `src/engine/starBattle/count.ts`——独立的精确解计数器及其预算受限变体；只用于测试交叉验证，
  绝不是生产门槛。
- `src/engine/starBattle/analyze.ts`——在同一套规则集上做的推理深度分析。
- `src/application/starBattleReducer.ts`——对局状态迁移：锁定、计分、撤销与唯一的获胜判定。
- `src/workers/starBattleWorker.ts`——带取消与过期结果保护的类型化 Worker 适配层。
- `src/ui/starBattleStore.ts`——闭包私有的 store：生成生命周期、持久化的难度偏好，以及带页面
  可见性保护的获胜间歇定时器。
- `src/ui/components/GamePicker.tsx` 与 `src/ui/components/StarBattleSurface.tsx`——应用入口与
  整个第二款游戏，都是纯 props 驱动的视图，样式由 `src/styles/starbattle.css` 提供。

### 唯一解是被证明的，绝非假设

字面上的需求「每加一颗雷都必须让数字保持唯一解」，在任何大于 1 × 1 的棋盘上都**不可能**字面
满足：第一颗雷放下之后，仍然有很多种放法能满足唯一解，因此几乎每一次添加都会失败。实际实现的
契约是这样的：

1. 已接受集合初始为空。
2. 每颗候选雷以**事务方式**加入；只有当存在一个完整的目标密度布局、它包含已接受的全部地雷、
   满足每行每列的覆盖要求，且其推导出的数字标注**唯一解**时，这颗雷才被接受。
3. 否则回滚该候选，另择一颗。
4. 达到目标雷数时，对真正要交付的棋盘**重新独立地**跑一次唯一性证明。

因此交到玩家手上的棋盘，一定恰好具有目标雷数、每行每列至少一颗雷、且只有一个解——而最后这一
条是在交付时重新证明的，而不是沿用构建它的那次搜索结果。

### 处处失败关闭

每一个有界搜索——行图案、唯一性、难度——在预算耗尽时都返回 `unknown` 而不是猜测，只有**完成**
的搜索才可能返回 `unique` 或 `multiple`。行图案默认最多 10,000 个完整图案与 300,000 个物化格；
LRU 缓存最多保留 256 个完整条目与 1,000,000 个格子，且只有完整枚举才允许入缓存。取消、零预算与
超时的截止期限都会失败关闭，界面会显示带有类型的诊断信息，而不是一张它无法背书的棋盘。

## 开发

```sh
npm ci
npm run lint
npm run typecheck
npm test
npm run build
npm run verify:base   # 断言所有构建产物都能在 /minegram/ 下解析
```

本地运行游戏用 `npm run dev`；构建并以生产模式预览用
`npm run build && npm run preview`。

Vite 的生产环境 base 路径是 `/minegram/`，GitHub Pages 工作流会把 `dist/` 部署到该 base 之下。
`verify:base` 之所以存在，是因为根绝对路径的资源 URL 在 `vite dev` 下完全正常，只在生产环境失效。
