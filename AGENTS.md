# Minegram Project Rules

## Product
Minegram is a client-side ordered mine-run puzzle game deployed through GitHub Pages.

## Runtime and Stack
- Node.js 24+ and npm.
- TypeScript, React, Vite, Vitest.
- No backend or runtime secret.
- All generator/solver code must remain independent of React and DOM APIs.

## Git Workflow
- This is a personal project: use a topic branch and worktree for implementation, create focused GPG-signed commits, then merge to `master` and push `origin` after all required verification passes.
- Never include unrelated changes. Never disable commit signing.
- **Never `git add -A` while a writer lane is running.** A designer's in-flight edits sit in the
  shared worktree, so a blanket add silently folds a half-finished lane into an unrelated commit
  and a reset afterwards is the only way out. Stage explicit paths, and read
  `git show --stat` before believing a commit is as small as its message claims.
- The remote is `git@github.com:SteamedFish/minegram.git`.

## Agent Model Policy
- Every AI agent and sub-agent must use `opencode/space-bunny-free` (Space Bunny Free) without fallback.
- **Temporary exception, granted 2026-09-25:** the user authorised other models when Space Bunny
  Free rate-limits (`space-bunny-free rate limit 了，可以暂时使用其他模型工作`). A 403 from that
  provider is a licence to switch, not a reason to stall. The default stays Space Bunny Free.

## Architecture
- `src/domain/`: pure types, board and ordered line clues.
- `src/engine/`: deterministic RNG, constraint solver, difficulty analysis, transactional generator.
- `src/application/`: game reducer, derived line progress, generation controller.
- `src/workers/`: typed Web Worker adapter for CPU-heavy generation.
- `src/ui/`: React components and user interaction.
- `src/styles/`: visual system and responsive rules.

Dependencies point inward: `domain <- engine <- application <- ui`; the worker adapts the engine without changing domain types.

## Generation Contract
- Every accepted board is independently proven to have exactly one mine solution.
- Literal unique-prefix growth is impossible after the first mine on a non-1×1 board. The accepted interpretation is transactional growth: every added mine must participate in at least one uniquely solvable full-size completion; otherwise the addition rolls back. The completed board receives a fresh independent uniqueness proof.
- All randomness comes from a seeded generator. Never use `Math.random()` in production engine code.
- Unknown/budget-exhausted solver results are failures, never treated as unique.
- Generation runs in a Worker and supports cancellation and stale-result protection.

## Gameplay Contract
- Default board: 15×15, 60% mines, initial score 5.
- Supported board range: 1..24 per side, at most 576 cells. `MAX_BOARD_SIDE` / `MAX_BOARD_CELLS` in `src/domain/board.ts` are the single source of truth and the settings form must read them instead of repeating a literal. The ceiling is the solver's per-line legal-pattern enumeration (10,000 patterns / 300,000 materialized cells per line): a ~25-cell line carrying the required internal blanks no longer fits that budget, so every larger board exhausts the resource limit and fails closed with `resource-limit`. Measured over 25 seeds at 60% density with a 30s budget: 0/24 failures at 24x24 (slowest 968ms) versus 5/24 at 25x25, then 2/2 at 26x26, 28x28 and 30x30. Larger solver-node budgets (400k/1.6M/6.4M) and a 600s time budget do not change the outcome, so this is a capacity fact, not a search-effort problem.
- Final boards contain at least one mine in every row and column.
- Ordered run clues preserve sequence; internal separators require at least one blank.
- Correct marks lock, and a locked cell rejects any later assertion. Wrong marks cost one point and may be corrected without refund. Score is clamped to zero and zero ends the game.
- Re-asserting the mark a cell already carries is free. A cell is charged only when its mark is changed to a different value and that new value is wrong.
- A drag applies each cell at most once and previews its score cost before commit.
- Correct completion of every cell wins and automatically generates the next puzzle with the same settings and a new seed.
- **Silent inert assertions.** An assertion that cannot change anything says nothing. Concretely: a re-assertion of a mark the cell already carries is free and silent, and a gesture whose every cell is locked is inert and silent, so it charges nothing, changes nothing, and announces nothing. The controller enforces this structurally rather than by special-casing: `previewMarkBatch` in `src/application/gameReducer.ts` skips locked cells, so an all-locked batch reports `affectedCount === 0`, and the drag controller commits only when `affectedCount > 0` — so no dispatch is ever issued. The reducer would still answer `ignored(state, 'locked-cell')` if it were asked, and the store would publish it; the refusal machinery in `src/ui/reasonCopy.ts` is defence in depth behind a correctly inert UI, not dead code, and must not be deleted because the pointer cannot currently reach it. A locked cell already shows its state visually, and a keyboard player gets the same answer. A refusal that *is* dispatched must be announced with a localised label, never a machine token.
- **Win interlude.** A won round holds its banner for 2500ms and then generates the next round automatically, because auto-advance is part of the contract; the interlude never elapses while the document is hidden, so a backgrounded tab cannot consume a round. A player who prefers to act is not blocked: the banner's own primary control starts the next round immediately, so waiting out the interlude is a default and never a gate. There is deliberately no second new-round control in the board toolbar; the banner is the single place the round result is stated, and a duplicate control would restate it.
- **Run highlight.** A run's numeral lights as soon as **every one of its mines is marked**, and that is the whole condition. It must not additionally require a proved start or a marked separator, because the player marks mines — filling gaps is the game's job, and the auto-reveal fills a whole line on exactly that condition. A stricter highlight is a bug report, not a stronger guarantee: it made a player who had placed three of the four runs of a `7 2 2 1` column see only the first one lit. `src/application/lineProgress.ts` reads a run's window off the solution when the clue cannot force a start, and `complete` is the mark test alone; a run with neither a solution nor a forced start stays open, which is the conservative answer. **`start` and `invariant` report the pure deduction; `end` does not.** When the solution pins a run's end but leaves its start free, `end` is reported and `start` stays `null`, so `end !== null` is not a proof of position — which is why the renderers test `invariant` *and* "not exactly one of the two ends is null", together. A consequence worth recording, because it makes the defect hard to reproduce: marking every cell of a run's window *forces* that run's start, so the deduced path takes over and `complete === true` with `start === null` is unreachable whenever marks are supplied. The reachable proof that a window is inference, not deduction, is a non-empty `mineIndices` alongside a null `start`; `src/application/lineProgress.test.ts` pins exactly that.
- **Hints (提示) are a preference, OFF by default, and the layer is exactly the annotations keyed off machine inference.** Three members: the `矛盾提示` cell — dashed border plus ✕ — the `进度未解` cell — dotted border plus ? — and, since the player's question of 2026-09-25 「段落位置已定 这个应该也属于提示？」, the open run's **position tape** (段落位置已定, the underline under a run whose position the solution has forced). They are off until the player turns them on, at any time, without costing a point. **What is NOT the hint layer, and must never be made switchable:** a run's numeral highlighting once every one of its mines is marked, its CLOSED run tape, and the line's ✓ badge. The player called that 必须做的 — mandatory — and it is the game's acknowledgement that they finished something, not an assist. A switch that could take it away would be a switch that can make the game unplayable, which is why the earlier reasoning that a clue numeral "cannot be off" stands: it is not a preference, it is the feedback the marking is for. Do not re-litigate this boundary on the grounds that the annotations would look tidier bundled with the highlight.
  **The membership rule is INFERENCE versus ACKNOWLEDGEMENT, and it is a code fact rather than a reading of the player's word.** A member of the layer says something the MACHINE worked out that the player has not done; a non-member says something the PLAYER has done. `RunGuides` (`src/ui/components/BoardSurface.tsx`) returns `null` unless `run.invariant` — the solution has pinned the run's window — and only then paints `data-run="tape"`, so an open run's tape is inference, while `data-run="complete"` is keyed off `run.complete`, which is derived from the player's own marks, and is therefore an acknowledgement. The same cut separates the ✓ and the filled numeral (acknowledgement) from `contradiction` and `unknown` (a pattern search the player cannot see). This rule is what decided the tape, and it is the rule to apply to any future candidate: name what the machine deduced, or name what the player finished. If a candidate fits neither, do not add it and do not remove it on taste — ask. Note that the previous grounding — the word 提示 appearing in exactly two legend cues — reached the right answer for the wrong reason, and would have kept the tape outside the layer forever while the player was still asking about it. At `data-hints="off"` the three annotations render nothing at all — no dashed edge, no dotted edge, no ✕, no ?, and no position tape under any run; at `on` they are conspicuous, because the player's other complaint about them was that they were easy to miss. The `aria-label` is deliberately exempt and stays unconditional, because for a screen-reader user it is the line's only channel of state and gating it deletes information rather than presenting it differently. Four boundaries, all load-bearing:
  - **The hint layer is not the auto-reveal.** Filling a line the player has finished is part of the win contract from the original specification — a round is won by marking its mines — so it can never be switched off. Hiding a marker the player already placed is a presentation choice; deleting the machine's own work would break the game. A change here must not touch `revealEligibleLines` or `roundIsComplete`.
  - **The hint layer is not a generation setting.** It lives in `useStoredFlag` under `minegram.hints` beside the theme and the panel toggles, never in `SettingsDraft`. `onChange` is the draft the generator reads; a player who flips a hint mid-round must not have their typed seed reprinted on the next Generate. `src/ui/components/hintsToggle.test.tsx` pins the panel field, the `role="switch"`, the dictionary wiring and the storage round-trip.
  - **When it is on it must be loud.** A default-off flag that switches to an easy-to-miss marker has not answered the request, only relocated it. The three annotations have to read as an obvious state change, not a tint — a dashed hairline and a small ✕ are exactly what the player already called too subtle.
  - **The hint layer is not the completion highlight, and a gate that grows is a bug.** This boundary has already been got wrong once, so it is written down as a trap: the hint layer was briefly widened to include the ✓ and the run numeral's on-state, on the reasoning that "deduced progress" was a tidier description. It was not tidier, it was wrong — those two are mandatory. `BoardSurface.test.tsx` pins all four phases, so a gate that grows fails a test rather than needing someone to notice. A future change that wants the layer to include more must first answer why the marking feedback can be switched off, and the answer cannot be "it would look more consistent".
- **Auto-reveal.** When every mine in a row or column is correctly marked and that line holds no incorrect mark, the reducer itself fills every remaining cell of that line as a correct, locked `blank` in the same commit as the batch that triggered it. The player is never charged for a cell the game filled, and the game must never write a mark that is wrong for the solution. Revealing is a property of the mark array, never of the renderer: a line the player filled by hand and a line the game filled must be indistinguishable in the stored state, and the game must announce which lines it filled. A round is won when every cell carries a correct mark, which is reached as soon as every mine is marked **and** no line whose mines are all marked still carries an incorrect mark; a round holding an incorrect mark is not won, and correcting it is the player's job. The reveal never runs when a round is accepted or when a round holds no mark at all, and it is idempotent: one pass over rows then columns is already the fixpoint, because a write lands only on a cell that is not a mine and can therefore neither complete a line nor break one. `roundIsComplete` in `src/application/gameReducer.ts` stays the single win predicate; the win check must run **after** the reveal, or the batch that marks the last mine soft-locks the round.
- **Star Battle auto-fill.** `fillStarExclusions` in `src/application/starBattleReducer.ts` fills, in the same commit as the batch that marked a **correct** star, that star's rest-of-row, rest-of-column, every other cell of its colour, and its 3 × 3 neighbourhood as `STAR_LOCKED` blanks. Three boundaries are load-bearing and each one exists because the alternative is a broken game, so none of them may be relaxed to "look tidier":
  - **It fires only on a correct star.** That is what makes it leak-free: row, column, colour and adjacency are all exclusions the rules already imply, so the fill records deduction the player could have made and never discloses where a remaining star *is*. Widening it to a wrong assertion would hand out the answer.
  - **It must never overwrite a mark the player made**, including a wrong star they already paid a life for; that mark stays visible so they can still see and fix it, and the round is not won while it stands. This is structural, not conditional: the inner `fill` returns unless the target is `STAR_UNMARKED`, so a player mark and a locked cell are both unreachable. Do not "fix" a double-charge by letting the fill win the cell instead.
  - **It is idempotent and free.** Every write lands on a cell that is blank in the solution, so one pass is already the fixpoint and no filled cell is ever charged. A filled cell is a property of the mark array, never of the renderer — a blank the player typed and a blank the game filled are indistinguishable in stored state, exactly as in Minegram's auto-reveal. `roundIsComplete` stays the single win predicate and the win check runs **after** the fill, or the batch that places the last star soft-locks the round. Because a correct star locks immediately and a locked cell refuses every later assertion *including retraction*, filled cells can never need undoing; that is the reason the feature is safe, so it is worth knowing before proposing "let the player clear a filled cell".
  The proof that the fill cannot silently eat a real star — placing one correct star leaves every other solution star `STAR_UNMARKED` across 24 boards × 3 tiers — is asserted in `src/application/starBattleReducer.test.ts`. Keep it if the fill is ever touched.
- **Star Battle lives, not score.** A wrong *star* costs one life (`DEFAULT_STAR_LIVES` 5, `MIN_STAR_LIVES` 1, `MAX_STAR_LIVES` 9, configurable, persisted under `minegram.star-battle.lives`), clamps at zero, and zero loses. A wrong *blank* is not chargeable — an untrue blank cannot be distinguished from a player's note — so only a claimed star can cost anything. There is deliberately no score alongside lives: the old `score` only ever fell by one per mistake, so it was lives under a misleading name, and shipping a configurable maximum next to it would have been incoherent.
- **Star Battle gestures and the deleted counters.** A tap marks a **star**; right-click or a 500 ms long-press toggles **blank**; drag paints the stroke's own tool once per cell. This is not arbitrary and must not be "tidied" back: the previous mapping had left-click cycling blank, which on a phone left marking a mine undiscoverable, because touch has no right-click and a 500 ms long-press is invisible — the player reported 「不知道怎么切换雷或者空白」. The row / column / colour counter groups and their ✓/✗ badges are **deleted** at the player's request (「我感觉上面的图例是冗余的…不如改成游戏规则说明+图例」): they only restated what the board already shows, so the space became a rules block and a mark legend that state the rules and the gestures in words. **The proximity-conflict outline must survive that deletion** — adjacency is the one rule with no count to read off the board, so it is the only conflict the game still draws, and removing it along with the counters would leave the third rule with no feedback at all.
- **Star Battle colour regions are contiguous, and that is structural.** `construct.ts` paints **strips + a sea**: the first two stars take the two edge columns, each tier lays a set of horizontal strips, and everything unclaimed absorbs into one sea region. After painting, the generator **counts connected components per colour and rejects any board where a region splits** — that rejection is the guarantee, not an optimisation, and it must not be deleted because it has "never fired" (it does not fire, because the construction is exact; that is the proof working, not the check being dead). The property came from the player's 「同一颜色的格子组成的色块全部连续，不分裂」, and the measurement that motivated it is the thing to remember: the previous chain construction produced **zero** fully-connected boards at *every* tier, with `starter` the worst (worst region 13 pieces at n = 10, 25 at n = 15) — so "the easy tier is fine" was a wrong inference, and it would be wrong again. Connectivity was reached *inside* the existing validity-window freedom, so the propagation certificate and uniqueness are untouched; any future change that adds a constraint to buy connectivity has given something up and needs the same scrutiny. n = 4 and 5 have **no** admissible `T` with the two edge columns taken (only 2 admissible permutations exist at n = 4, 14 at n = 5), so they use a parented-domino construction; the briefed uniform-random fallback was measured at 7/2000 and 0/2000 connected and is literally unfillable, which is why the fallback looks different.
- **The sea is a hub — and I over-claimed what that ruled out.** The sea is adjacent to **every** other region at every board size and every tier, so no region renumbering and no hue assignment can move its colour away from anything; that part is structural and true. What I wrongly concluded from it was that 「相近颜色的色块尽量远离」 was *only half-achievable in layout*, i.e. that the hub was unavoidable. It is not — the hub comes from the strips+sea construction, not from the rules. The correction is measured, not argued: **four boards the player picked out of the game they actually enjoy were measured and none of them has a hub.** Their largest region is 25–40% of the board (36% / 40% / 25% / 30%) against our 39–59%. So the hub is a *construction* fact to be designed away, and 「相近颜色尽量远离」 is fully achievable in layout if the construction stops forcing a hub. I recorded the wrong conclusion in this file before having the evidence that overturned it, which is the reason to read the measurement below rather than trust my earlier reasoning. One shape to note for whoever builds it: board D has a region adjacent to 8 of the other 9 — near-hub without being one, and it is among the boards the player found interesting. Two consequences that are NOT hub-related must not be "fixed" while a hub-free construction is built: `starter` lays no strips, so the sea covers 81% of the board at n = 4 and 94% at n = 15 and a starter board legitimately reads as a field with n distinct single cells on it — that is the construction working, not a degenerate board; and the n = 6–8 `steady`/`challenging` collision (`s = round(0.7n)` made the strip sets equal) is **pre-existing and deliberately unretuned**, because changing a shipped difficulty band is a product decision rather than a side effect of this work.
- **Shape is not a gate; difficulty is. A hub or whole-line board is a legal board and must stay generatable.** The player's ruling: 「只要是合法的满足规则的棋局都要有概率被我们构建出来才行」 and 「偶尔小概率出现而不是一直出现，没关系，只要合法，不用刻意排除，只是难度可能会变低，在高难选项里面如果计算发现难度不够再排除」. So the generator carries **no shape exclusions at all** — hub regions, whole-row or whole-column colour bands, a dominant 90% region, all of it is legal and appears at whatever probability the natural measure gives. A tier rejects a board only when the **difficulty measurement** says the board is too easy, which is a consequence rather than a rule about shape. This retires the hub gate and the whole-line gate I was about to build: both are *already* difficulty signals, because a whole-line region hands over n − 1 free blanks and a hub hands over a great deal, so an instrument that counts freebies in blank marks rejects them from the hard tiers automatically and lets them into the easy ones. **The corollary is that the difficulty instrument has to count blank marks, not solver work** — see the next bullet, which is the same lesson learned twice.
- **Measure what the game hands the player for free in GAME-RULE terms, never in solver terms — I have now made this mistake twice.** A colour that owns an entire row resolves that whole row for free: the row's one star must be that colour, and since each colour has exactly one star, every other cell of that colour is blank, so the row is determined but for a single cell — n − 1 free blanks at n = 10, plus the fact that no other colour appears there at all. I measured exactly this property (1 such line on 100% of non-starter boards) and judged it **weak**, because *my* derivation from the rules reached only one deduction. The player's derivation reached n − 1. That is the second time the same error took a different shape: first wave count as a difficulty proxy, then solver propagation depth as a "how much is free" proxy. **A solver measures what the solver does; it does not measure what the player is given.** Any structural gate — hub, share cap, whole-line — must be justified by a consequence the player can read off the board, and the freebie must be counted in blank marks, not in solver steps. A gate that a solver cannot see is a gate that does not exist: the current 40% largest-region budget is blind to this, because at n = 10 a whole row is only 10% of the board.
- **The Star Battle palette optimises the WORST pair, not the neighbouring pair.** The rule in `src/styles/starbattle.css` is a 5 hue slots × 4 lightness levels grid with the hue shifting 36° per level, tuned for **maximum minimum pairwise CIEDE2000 over every prefix of 4..20** colours. Any two colours can end up adjacent on a board, so only the worst pair matters and "make adjacent indices look different" is the wrong objective — a change that reorders hues to space out *consecutive* indices would reintroduce the exact defect the player reported (the old palette's worst pair measured ΔE00 ≈ 4, i.e. indistinguishable). Hue alone cannot carry 15 colours: 15 evenly spread is 24° apart, already at the edge of eye resolution for flat patches, so lightness is spent deliberately and no third (hatch/glyph) channel is needed. Light and dark are two separate palettes, never inversions of each other. `src/styles/starbattle.palette.test.ts` pins the measured separations and self-validates its ΔE00 against Sharma reference values; if a future palette change drops the worst pair, that test is the thing that will notice.
- **Star Battle difficulty names a technique count, and that count is not a difficulty scale.** Five tiers: `starter` / `steady` base rules alone finish the board (shallow vs long chain); `challenging` base stalls and exactly one confinement idea is needed; `expert` base stalls and no single idea suffices; `contradiction` base stalls and *every* confinement subset fails, so only proof by contradiction works (`入门/进阶/挑战/专家/反证` in the UI, `反证` rather than `矛盾` because 矛盾 already means the adjacency-conflict outline). The count is enforced per accepted board by enumerating all sixteen subsets, and the `contradiction` tier is measured at 60/60 acceptance for n = 8/9/10 with **every** board at `csPasses=1`. **Do not present this as calibrated human difficulty.** Measured against four boards the player singled out as interesting, the count does not fit them: A is k=2 (5 witness waves), B is k=-1, C is **k=1 with 12 witness waves** and is the board rated highest, D is k=2 (8 waves) — our easiest k=1 boards take 4 waves. Waves themselves do not separate the levels either (k=1 boards span 3–5 waves, k=2 4–8, k=-1 3–8). Two dead instruments, both retired: the **leave-one-out fingerprint** (`fingerprintStarCatalogue`) reports a rule as load-bearing even when another single rule reaches the same place — board C's fingerprint is non-empty while four of four singles solve it — so it must never grade anything; and **`wave count`** measures solver grind, not human effort.
- **`c1` and `c2` are ONE technique under two labels, and the zone generator was non-monotonic until the matching rewrite.** `catalogue.ts` dispatches `j === 1 ? 'c1' : 'c2'` off a single generator, so counting rule ids double-counts one idea; `measureMinimumBasis` therefore counts *ideas*. The bigger trap: zones used to be derived from a union closure over colour footprint masks capped at `popcount <= 3`, which meant **more available rules could make a board UNSOLVABLE** — measured, `{base,c1,c2}` solved a board 10/10 while adding `c3` *or* `c4` stalled it at 0/10, because the extra rules' sound blanks shrank a footprint until a legal zone became unrepresentable. It is now an uncapped Hall/matching propagator (starless colours ↔ starless lines, Kuhn matching with Dulmage–Mendelsohn SCC analysis), which is monotone by construction because sound blanking only removes graph edges. **This is why acceptance must never infer a subset solve from a full-catalogue solve**: upward-closure is not a property you get for free, so the sixteen-subset enumeration runs inside `measureMinimumBasis` on every accepted board and asserts it. That enumeration is also what makes the old `popcount <= 3` cap's damage visible — lifting it reclassified 21 boards from "requires contradiction" to "needs j>=4 confinement", because a human reads four colours sharing four lines as direct deduction and needs no assumption.
- **Locale and copy.** The store is the single source of truth for locale: a persisted language preference must be applied to the store on mount, not only when the player actively changes the language, because every snapshot-projected player-facing string (failure headlines, remedies, announcements, reason labels) is composed from the store's own dictionary and closure `locale` — a store that never learns the restored preference projects English copy inside a Chinese tree, silently and only for returning players. A component that builds a copy object inline instead of using the projection helpers (`projectResume` and its siblings in `src/ui/viewModel.ts`) must interpolate its own templates at the producer; `interpolate` deliberately leaves an unknown placeholder verbatim so a missing value stays visible, which makes the producer — never the interpolator — the bug when a raw `{name}` reaches the player.
